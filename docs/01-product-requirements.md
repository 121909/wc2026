## 1. 产品定义

系统在本地观察《炉石传说》桌面客户端，将日志和画面转换为结构化对局状态，结合卡牌规则、环境卡组和对手行为生成决策。在安全条件满足时，系统可以将已验证的动作转换成客户端输入，并持续记录结果供复盘和统计。

本文中的“最优解”定义为：在隐藏信息、随机性、计算预算和回合时间限制下，当前可观测信息中**预期获胜概率最高的合法动作序列**，不表示数学上的全局最优。

## 2. 产品目标

- 支持可配置、可替换的 OpenAI 兼容模型服务。
- 可靠获取用户卡组、模式及当前对局状态。
- 建立可按补丁更新的卡牌数据库。
- 每日同步主流卡组，并随对局事件缩小对手卡组范围。
- 支持起手换牌、回合规划和特殊选择决策。
- 在状态不确定或执行异常时停止自动输入。
- 生成按职业、卡组原型和先后手划分的每日战绩报告。

## 3. 使用角色与运行模式

主要角色是本机操作者。系统提供四级运行模式：

1. **观察模式**：只读取和记录状态。
2. **建议模式**：展示换牌及出牌建议，由用户执行。
3. **监督执行模式**：系统准备动作，用户确认后执行。
4. **自动执行模式**：通过安全门槛后自动执行，用户可随时接管。

默认运行模式为建议模式。运行模式的提升必须由用户显式操作，不能因重启自动升级。

## 4. MVP 范围

第一版限定：

- Windows 桌面客户端。
- 单一客户端语言，初始建议使用简体中文或英文中的一种。
- 标准模式，暂不覆盖狂野、竞技场、酒馆战棋等差异较大的模式。
- 一个己方卡组原型，优先选择操作线性且随机效果较少的卡组。
- 固定的推荐窗口模式及少量已校准分辨率。
- 支持常规换牌、出牌、攻击、目标选择、发现和结束回合。
- 自动执行仅在练习、冒险或双方知情的友谊赛中验收。

## 5. 功能需求

### 5.1 模型服务配置

| ID | 需求 |
| --- | --- |
| CFG-001 | 支持保存多个 OpenAI 兼容服务配置，包括名称、Base URL、模型和能力信息。 |
| CFG-002 | API Key 只能来自系统凭据存储或环境变量，不能明文进入普通配置和日志。 |
| CFG-003 | 支持自定义请求头、超时、重试、代理、并发和用量上限。 |
| CFG-004 | 启动时检测结构化输出、工具调用等能力，不假定所有兼容服务功能一致。 |
| CFG-005 | 服务不可用或输出不符合协议时，停止依赖该结果的自动输入并记录原因。 |

### 5.2 卡组与模式

| ID | 需求 |
| --- | --- |
| DECK-001 | 支持通过卡组代码导入卡组，并解析格式、职业及卡牌数量。 |
| DECK-002 | 用户可以选择己方卡组、游戏模式和运行模式。 |
| DECK-003 | 对局开始时校验实际英雄、模式和预期卡组，发现冲突时禁止自动执行。 |
| DECK-004 | 追踪己方原始牌库、已抽牌、已使用牌、生成牌、洗入牌和变形牌。 |

### 5.3 卡牌与环境数据

| ID | 需求 |
| --- | --- |
| DATA-001 | 卡牌定义包含稳定 ID、多语言名称、费用、类型、属性、文本、关键词和可用模式。 |
| DATA-002 | 数据按游戏构建号或补丁版本保存，平衡调整后不覆盖历史对局依赖的旧定义。 |
| DATA-003 | 记录衍生、召唤、发现、变形等卡牌关系以及结构化效果标签。 |
| DATA-004 | 每日从允许使用的数据源同步主流卡组，记录来源、模式、地区、分段、样本量和时间。 |
| DATA-005 | 同一卡组的不同来源和少量替换版本可以规范化、去重及归入同一原型。 |

### 5.4 状态与记牌

| ID | 需求 |
| --- | --- |
| STATE-001 | 从游戏日志建立主事件流，画面识别仅补充日志无法确认的信息。 |
| STATE-002 | 状态至少覆盖英雄、资源、手牌、牌库、战场、武器、地点、奥秘、任务、附魔和回合历史。 |
| STATE-003 | 每个状态字段具有来源、更新时间和置信度。 |
| STATE-004 | 区分原始构筑卡与生成、偷取、复制、变形、洗入的卡，避免错误排除对手卡组。 |
| STATE-005 | 状态发生断档或冲突时尝试重放和重新同步；仍不确定则降级运行模式。 |

### 5.5 对手卡组推断

| ID | 需求 |
| --- | --- |
| META-001 | 根据职业、模式、补丁、地区和分段建立初始候选卡组及先验概率。 |
| META-002 | 对方每展示一张有意义的卡后更新候选概率，并展示 Top 3 与置信度。 |
| META-003 | 允许构筑变体、可选卡位、多职业牌和附属卡组，不做简单的绝对包含判断。 |
| META-004 | 低于相似度门槛时标记为未知卡组，保存已展示的原始牌库卡。 |
| META-005 | 未知样本可以在离线任务中聚类，但未经确认不能自动写成权威主流原型。 |

### 5.6 对局决策

| ID | 需求 |
| --- | --- |
| DEC-001 | 起手阶段根据己方构筑、先后手和对手原型分布给出逐卡换牌决定。 |
| DEC-002 | 回合中生成合法动作序列，而不只给出单步卡牌名称。 |
| DEC-003 | 优先使用确定性算法检查斩杀、防斩杀、费用、目标和动作顺序。 |
| DEC-004 | 模型只能在结构化状态、卡牌查询结果和合法候选范围内进行策略选择。 |
| DEC-005 | 每次决策保存候选、评分、最终动作、使用的信息和简短理由。 |
| DEC-006 | 必须为发现、随机选择、目标选择、奥秘试探和回合超时预留策略。 |

### 5.7 输入执行与监督

| ID | 需求 |
| --- | --- |
| EXEC-001 | 高层动作与鼠标键盘输入分离，执行器不能自行制定策略。 |
| EXEC-002 | 每个动作具有前置条件、预期结果、超时和失败恢复方案。 |
| EXEC-003 | 找不到元素、窗口失焦、状态置信度不足或回合归属不明时不点击。 |
| EXEC-004 | 提供全局暂停、人工接管和紧急停止，停止后不自动恢复。 |
| EXEC-005 | 执行前后保存足够的脱敏诊断信息，支持问题复现。 |

### 5.8 统计与报告

| ID | 需求 |
| --- | --- |
| REPORT-001 | 保存对局结果、时间、模式、卡组版本、先后手、对手职业及推断原型。 |
| REPORT-002 | 生成每日总对局数、胜负、胜率、平均时长、异常数和排名变化。 |
| REPORT-003 | 输出按职业、对手原型和先后手划分的胜率，同时展示样本数。 |
| REPORT-004 | 保存未知卡组和低置信度识别列表，供人工复核。 |
| REPORT-005 | 记录模型调用次数、延迟、失败率及估算费用，但不记录密钥。 |

## 6. 非功能需求

- **合法性**：系统提交给执行器的非法动作率目标为 0。
- **状态准确性**：受支持场景的离线回放状态还原准确率达到 99% 以上；关键动作前状态必须达到更高门槛。
- **时延**：常规决策目标 3 秒内完成，复杂决策目标 8 秒内完成，并保留动画及输入时间。
- **可复现性**：给定相同数据版本、事件流和模型响应，可以重建决策过程。
- **可恢复性**：进程重启后可恢复记录，但不能未经用户确认恢复自动输入。
- **隐私**：默认本地存储；上传模型的内容最小化并可审计。
- **可升级性**：游戏补丁变化不得静默污染旧数据或历史统计。

## 7. 明确不做

- 不做进程注入、内存扫描、网络封包拦截、反检测和安全机制绕过。
- 不承诺达到任何具体段位或长期胜率。
- MVP 不覆盖所有模式、语言、分辨率和卡牌交互。
- MVP 不在线训练会直接改变生产决策的模型。
- 不从来源不明或禁止自动访问的网站采集数据。

## 8. 产品级验收

MVP 完成需同时满足：

1. 使用一套指定标准卡组完整记录至少 100 个可重放测试回合。
2. 所有测试回合均能构造合法动作集合，非法输入为零。
3. 对正常日志重放达到状态准确性目标，异常样本能明确降级或暂停。
4. 起手与回合建议具有可读理由和所依据的数据版本。
5. 对手候选概率会随有效卡牌证据收敛，生成牌不会污染推断。
6. 日报能够从测试数据重复生成相同聚合结果。
7. 自动输入仅通过受控环境验收门槛，不作为公开匹配验收项目。

## 9. 编码前待确认事项

- MVP 客户端语言和第一个支持卡组。
- Windows 最低版本及目标游戏窗口模式。
- 首选卡牌和环境卡组数据源及其授权条件。
- 最终实现语言与桌面技术栈。
- 是否需要完全离线的本地模型备选方案。
- 原始日志、截图和对局记录的默认保留周期。
